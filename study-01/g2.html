フロントエンド実装

HTML/CSS実務

セマンティックHTML意味に沿ったタグ選び ボックスモデルの理解 Flexbox・Gridでのレイアウト レスポンシブデザイン画面幅に応じた最適化 CSS設計手法命名規約・スコープ管理 ブラウザ間差異への対応

HTML/CSSは見た目だけの技術と誤解されがちだが、実際には構造と意味を正しく表現する技術である。見出しには見出しタグ、ボタンにはボタン要素を使うといったセマンティックHTMLは、後述するアクセシビリティやSEOの土台になる。レイアウトの基礎であるボックスモデルの理解がないまま余白や幅の調整を続けると、見た目の崩れを場当たり的なCSSで塞ぐ悪循環に陥る。

一人前のエンジニアは、Flexbox・Gridでのレイアウトを使い分けて、複雑な配置を最小限のCSSで実現できる必要がある。並びが1方向で良ければFlexbox、行と列の両方を制御したければGridというように、目的に応じた選択ができるかどうかで実装の保守性が大きく変わる。

実務で欠かせないのがレスポンシブデザインであり、スマートフォンからデスクトップまで画面幅に応じて最適な表示を提供することは、もはや前提条件になっている。またチーム開発ではCSS設計手法による命名規約やスコープ管理がないと、あるコンポーネントのスタイル変更が別の場所を意図せず壊す「CSSの副作用」が頻発する。加えてブラウザ間差異への対応は地味だが根強い落とし穴で、特定のブラウザでだけレイアウトが崩れるという不具合は、確認を怠ると本番で発覚しがちだ。

🔧 やってみよう

HTML/CSSで書いた既存ページを1つ選び、BEMなどの命名規則でクラス名を付け直し、レイアウトをFlexbox/Gridで組み直す。Chrome DevToolsのデバイスツールバーで複数の画面幅とブラウザでの見え方を確認する。所要目安45〜60分。

アクセシビリティ

セマンティクスとARIA属性 キーボード操作対応 スクリーンリーダー音声で読み上げる支援技術での確認 コントラスト比 フォーカス管理 アクセシビリティ監査ツールの活用

アクセシビリティとは、視覚・聴覚・運動機能などに制約のある人を含め、誰もが使えるようにUIを作る取り組みである。正しいセマンティクスとARIA属性の使用は、スクリーンリーダーを使うユーザーにボタンやフォームの意味を正確に伝えるために欠かせない。

これが一人前のエンジニアに求められる理由は、アクセシビリティが「あれば嬉しい追加機能」ではなく、法規制や企業のコンプライアンス要件になりつつあり、かつ多くのユーザーの体験を底上げする基礎品質だからだ。マウスを使わずタブキーだけで操作するキーボード操作対応や、視認性を確保するコントラスト比の確保は、健常なユーザーにとっても操作性の良さとして跳ね返ってくる。

実務での勘所は、フォーカス管理を後回しにしないことだ。モーダルを開いたときにフォーカスがどこに移るか、閉じたときに元の位置に戻るかといった細部を怠ると、キーボードユーザーは操作不能に陥る。すべてを手動確認するのは非現実的なので、アクセシビリティ監査ツールの活用によって機械的に検出できる問題を早期に潰し、人手でのレビューは判断が必要な部分に絞るのが現実的な進め方である。

🔧 やってみよう

自分が作ったフォームやページをマウスを使わずTabキーだけで操作し、フォーカスの移動順序を確認する。Lighthouseのアクセシビリティ監査を実行し、指摘事項を1つ以上実際に修正する。所要目安45分。

コンポーネント設計

再利用可能な単位への分割 Props親から渡す値とState内部状態の分離 コンポーネント間の責務分担 デザインシステム共通部品集との連携 過剰な分割の弊害

コンポーネント設計とは、UIを意味のある単位に分割し、それぞれが独立して理解・再利用できるようにする技術である。再利用可能な単位への分割ができていないと、同じようなUIをあちこちにコピペし、修正のたびに全箇所を探して直すことになる。

一人前のエンジニアは、Propsとstateの分離を意識してコンポーネントを設計する。親から渡された値であるPropsと、コンポーネント自身が持つ内部状態であるStateを混同すると、データの流れが追えなくなり、どこで値が変わったのか分からないバグが生まれる。コンポーネント間の責務分担を明確にし、「このコンポーネントは表示だけ」「あのコンポーネントはデータ取得だけ」といった役割分けができると、変更の影響範囲を予測しやすくなる。

実務での落とし穴は両極端にある。分割が足りなければ巨大で読みにくいコンポーネントができるが、過剰な分割の弊害として、小さすぎる部品に分けすぎるとファイルを何度も行き来しないと全体像がつかめなくなる。適切な粒度の見極めは経験がものを言う部分であり、また社内やOSSのデザインシステムと連携することで、車輪の再発明を避けつつ一貫したUIを効率よく組み立てられる。

🔧 やってみよう

既存の大きめのコンポーネントを1つ選び、Propsとstateを整理した上で2〜3個の小さいコンポーネントに分割する。分割前後でファイルの見通しがどう変わったかをメモに残す。所要目安60分。

状態管理

ローカル状態とグローバル状態の使い分け 状態管理ライブラリの選定基準 サーバー状態とクライアント状態の分離 キャッシュと再取得のタイミング 状態の正規化重複を避けた形での保持

状態管理とは、アプリケーションが今どのようなデータを持っているかを整理し、変更を予測可能な形で反映させる技術である。あるコンポーネントだけで完結する値はローカル状態に、複数の画面をまたいで必要な値はグローバル状態に置くというローカル状態とグローバル状態の使い分けができないと、無関係な変更が思わぬ場所の再描画を引き起こす。

一人前のエンジニアに求められるのは、とりわけサーバー状態とクライアント状態の分離という視点だ。APIから取得したデータ(サーバー状態)と、フォームの入力値のようにアプリ内だけで完結するデータ(クライアント状態)は性質が異なり、前者にはキャッシュと再取得のタイミングという固有の課題がある。この区別を持たずに全てを同じ仕組みで管理しようとすると、無駄な再取得や古いデータの表示といった問題が起きやすい。

実務では、状態管理ライブラリの選定基準を持たずに流行のライブラリを導入すると、プロジェクトの規模に対して過剰に複雑な仕組みを抱え込むことがある。小規模ならフレームワーク標準の機能で十分なことも多い。また状態の正規化を怠ると、同じデータが複数箇所に重複して保持され、片方だけ更新して整合性が崩れるというありがちなバグを招く。

🔧 やってみよう

フォームのローカル状態とAPIから取得したデータ（サーバー状態）を明確に分けて実装し直し、画面へのフォーカス復帰時に再取得するタイミングを1つ設定してみる。所要目安45分。

ブラウザ描画とパフォーマンス

レンダリングパイプライン描画までの流れの理解 再レンダリングの発生条件 仮想DOM差分計算用の中間表現の役割 レイアウトシフト表示中のガタつきの回避 画像・フォントの最適化読み込み

ブラウザは、HTMLとCSSを解析してから画面に描画するまでに複数の段階を経ており、このレンダリングパイプラインの理解がないと「なぜこの変更が遅いのか」を説明できない。ReactなどのUIライブラリが使う仮想DOMの役割は、実際のDOM操作を最小限にするための差分計算の仕組みであり、これを理解しておくと不要な描画コストを避けられる。

一人前のエンジニアには、再レンダリングの発生条件を把握し、意図しない再描画を防ぐ力が求められる。これを知らないままコンポーネントを組むと、一箇所の状態変化が画面全体を再計算させ、体感速度を悪化させることがある。

実務でユーザー体験を大きく左右するのがレイアウトシフトの回避だ。画像の読み込み前後でサイズが確保されておらず、コンテンツがガタつきながら表示されると、ユーザーは誤操作しやすくなり不快感も強い。画像・フォントの最適化読み込みによってサイズをあらかじめ指定し、必要なリソースを優先的に読み込む工夫をするだけで、体感速度は大きく改善する。

🔧 やってみよう

React DevTools（または相当のプロファイラ）で自分のアプリの再レンダリングを観察し、不要な再描画が起きている箇所を1つ特定してmemo化などで抑制する。抑制前後の再レンダリング回数を比較する。所要目安45分。

Core Web Vitalsユーザー体験の主要指標

LCP表示速度の指標 INP応答性の指標 CLS視覚的な安定性の指標 計測ツールの使い方 改善優先度の付け方

Core Web Vitalsは、Googleが定義したユーザー体験を数値で評価するための指標群であり、表示速度を示すLCP、操作への応答性を示すINP、視覚的な安定性を示すCLSの3つが中心となる。感覚的な「速い・遅い」を客観的な数値に変換できることが、この指標の価値である。

一人前のエンジニアがこれを知っておくべき理由は、パフォーマンス改善の議論を「なんとなく重い気がする」から「LCPが3秒を超えている」という具体的な会話に変えられるからだ。数値化された指標があることで、検索順位への影響やビジネス指標との関連づけもしやすくなる。

実務では、まず計測ツールの使い方を身につけて自分のサイトの現状を把握することが出発点になる。指標がすべて重要というわけではなく、サイトの特性に応じて改善優先度の付け方を判断する必要がある。たとえば画像の多いサイトならLCP、インタラクションの多いアプリならINPを優先するといった具合だ。数値だけを追いかけて本質的なユーザー体験の改善を見失わないようにする視点も欠かせない。

🔧 やってみよう

PageSpeed Insightsで自分のサイト（または任意の公開サイト）のLCP・INP・CLSを計測し、最も改善優先度の高い指標を1つ選んで実際に改善策（画像圧縮やサイズ指定など）を適用し、再計測して数値の変化を確認する。所要目安60分。
