開発プロセス

Git分散バージョン管理

commit・branch・merge の基本 GitHub Flow / Git Flow / トランクベース短命ブランチ中心 rebase履歴を積み直すとmergeの使い分け cherry-pick特定コミットだけ取り込む stash作業を一時退避 bisect二分探索で問題コミットを特定 reflog操作履歴からの復旧 コンフリクト競合解決 Conventional Commits規約に沿ったコミット文 タグとリリース運用 .gitignore と機密ファイル除外

commit・branch・mergeはGitの基本操作であり、GitHub Flow・Git Flow・トランクベース開発は短命ブランチを中心にするか長寿命ブランチを使うかといったブランチ運用の流儀の違いである。rebaseは履歴を積み直して直線的にする操作でmergeとの使い分けが必要になり、cherry-pickは特定のコミットだけを別ブランチに取り込む操作、stashは作業中の変更を一時退避する操作、bisectは二分探索で問題を作り込んだコミットを特定する機能、reflogは操作履歴から失った変更を復旧する機能である。コンフリクトの解決、Conventional Commitsという規約に沿ったコミットメッセージの書き方、タグとリリース運用、.gitignoreによる機密ファイルの除外も日常的に使う知識である。

Gitはチーム開発の基盤であり、rebaseとmergeの使い分けを誤ると履歴が読みにくくなったり、他人の作業を壊したりする。AIがコミットメッセージやブランチ運用を提案する場面が増えているが、チームの規約（Conventional Commitsの採用有無やブランチ戦略）に沿っているかを確認し、機密情報が誤ってコミットされていないかをレビューする力は変わらず人間の責任である。

実務でのよくある事故は、.gitignoreの設定漏れでAPIキーや秘密鍵がリポジトリに混入することや、rebase後のforce pushで共有ブランチの他人の作業を消してしまうことである。bisectやreflogは緊急時の強力な復旧手段であり、これらを知っているかどうかがインシデント対応の速度を大きく左右する。

🔧 やってみよう

意図的にコンフリクトが起きる2本のブランチを作り、mergeとrebaseの両方で解決してみて履歴の見え方の違いを比較する。所要目安: 45分。

テスト

単体テスト・結合テスト・E2Eテスト利用者操作の通し試験 テストピラミッド下層を厚くする配分 AAAパターン準備・実行・検証 モック偽物・スタブ{固定応答}・フェイク{簡易実装} パラメータ化テスト入力を並べて回す スナップショットテスト出力の差分比較 フレーキーテストたまに落ちる不安定な試験対策 カバレッジ網羅率の限界理解 テストデータとフィクスチャ準備データ 契約テスト連携先との取り決め検証

単体テストは関数やクラス単位の検証、結合テストは複数コンポーネントの連携の検証、E2Eテストは利用者の操作を通しで検証するテストであり、テストピラミッドはこの3層のうち下層（単体テスト）を厚く上層を薄くする配分の指針である。AAAパターンは準備・実行・検証の3段階でテストを構成する型、モック・スタブ・フェイクはそれぞれ偽物・固定応答・簡易実装で依存先を置き換える手法、パラメータ化テストは複数の入力パターンを並べて一括で検証する手法、スナップショットテストは出力の差分を比較する手法である。フレーキーテスト対策、カバレッジの限界理解、テストデータとフィクスチャの整備、連携先との取り決めを検証する契約テストも実務での重要な観点である。

テストはAIが生成したコードが本当に意図通り動くかを検証する唯一の客観的な手段であり、テストがなければAIの出力を信じるか信じないかの水掛け論になってしまう。テストピラミッドの考え方を理解していれば、E2Eテストばかりに頼って実行が遅く壊れやすいテストスイートを作ってしまう失敗を避けられ、AIにテストコードを書かせる際も適切な粒度を指示できる。

実務での落とし穴は、カバレッジの数値だけを追いかけて意味のあるアサーションを欠いたテストを量産することや、フレーキーテストを放置してCIの信頼性を失いチーム全体がテスト結果を無視するようになることである。契約テストは連携先とのAPI仕様のズレを早期に検出できる強力な仕組みだが、導入コストが高いため、マイクロサービス間の依存が増えてきた段階で検討すべき技術である。

🔧 やってみよう

既存の関数を1つ選んでAAAパターンで単体テストを書き、境界値(0件・1件・上限)を含むパラメータ化テストに拡張する。所要目安: 1時間。

CI/CD継続的統合・継続的デリバリー

パイプライン自動処理の流れ設計 キャッシュと並列化による短縮 リンタ規約違反の検出とフォーマッタ{整形} 静的解析実行せずに欠陥を検出 ビルド成果物アーティファクトの管理 デプロイ戦略ブルーグリーン／カナリア／ローリング フィーチャーフラグ機能の出し分けスイッチ ロールバック切り戻し手順 秘匿情報のCI設定

パイプラインはビルド・テスト・デプロイといった自動処理の流れを設計したものであり、キャッシュと並列化によって実行時間を短縮できる。リンタは規約違反を検出し、フォーマッタはコードを自動整形し、静的解析は実行せずにコードの欠陥を検出する。ビルド成果物（アーティファクト）の管理、ブルーグリーン・カナリア・ローリングといったデプロイ戦略、機能を出し分けるフィーチャーフラグ、問題発生時に切り戻すロールバック手順、CI環境での秘匿情報の安全な扱いもCI/CDの重要な構成要素である。

CI/CDはAIが生成したコードを含むあらゆる変更を安全に本番へ届けるための最後の砦であり、この仕組みが整っていなければAIの生産性向上がそのまま事故のリスク増大に直結してしまう。パイプラインの各ステージが何を保証しているかを理解していれば、AIが生成したコードをマージする前にどの検証を通す必要があるかを適切に判断できる。

実務での落とし穴は、CI設定に秘匿情報を平文で書いてしまうことや、デプロイ戦略を考えずに一斉切り替えを行い障害時のロールバックに時間がかかることである。フィーチャーフラグを活用すればデプロイとリリースを分離でき、問題があった機能だけを即座に無効化できるため、AI生成コードを段階的に本番投入する際の安全弁としても有効である。

🔧 やってみよう

GitHub Actionsでlint→test→buildの簡単なパイプラインを組み、依存関係のキャッシュを設定して実行時間がどれだけ短縮されるか計測する。所要目安: 1.5時間。

コードレビュー

観点リストの作成 要件充足・可読性・性能・安全性の順で見る 指摘の粒度と表現 nit些細な指摘の明示 レビュー依頼側の準備説明文・差分分割 承認基準とマージ条件 レビュー滞留の可視化

コードレビューでは観点リストを事前に作っておくと抜け漏れが減り、一般的には要件充足・可読性・性能・安全性の順で見ていく。指摘の粒度と表現、些細な指摘であることを示すnitの明示、レビュー依頼側が説明文を書き差分を適切に分割する準備、承認基準とマージ条件の明確化、レビューが滞留していないかの可視化も、レビュー文化を機能させる実務的な工夫である。

AIが大量にコードを生成できるようになった今、コードレビューは「人間が書いたかAIが書いたか」に関わらず品質を保証する最後の関門としてこれまで以上に重要性を増している。観点リストを持って体系的にレビューできる力がなければ、大量に生成されたコードを目視で流し読みするだけになり、意図と欠陥を見抜く前提が崩れてしまう。

実務での落とし穴は、些細な指摘（nit）と致命的な指摘を同列に扱ってレビューが長引くことや、差分が大きすぎてレビュアーが表面的な確認しかできなくなることである。レビュー依頼側が変更の意図を説明する文章を添え、差分を小さく分割する習慣を持つことは、AIが生成した大量の変更をレビューする際に特に効果を発揮する。

🔧 やってみよう

自分やAIが書いた直近の差分に、要件充足・可読性・性能・安全性の順で観点リストを当てはめてレビューコメントを実際に書いてみる。所要目安: 45分。

リファクタリング振る舞いを変えず構造を直す

メソッド抽出 変数のインライン化 条件分岐の単純化 早期リターン条件を先に弾く マジックナンバー意味不明な数値の定数化 神クラス何でも持つ肥大クラスの分割 ストラングラーパターン段階的に置き換える テストで守りながら進める

リファクタリングは外部から見た振る舞いを変えずに内部構造だけを改善する作業であり、メソッド抽出、変数のインライン化、条件分岐の単純化、条件を先に弾く早期リターンといった具体的な技法がある。意味不明な数値であるマジックナンバーを定数化する、何でも持ってしまった神クラスを分割する、大きな仕組みを段階的に置き換えるストラングラーパターンを使う、そして常にテストで守りながら進めることが基本原則である。

リファクタリングは「動いているコードを触る」という高リスクな作業を安全に行うための技術であり、AIに既存コードの改善を依頼する場面が増える中で、AIが提案するリファクタリングが本当に振る舞いを変えていないかをテストで確認できる体制があるかどうかが安全性を左右する。

実務での落とし穴は、テストが不十分な状態で大規模なリファクタリングに着手し振る舞いが変わってしまうことに気づけないことである。神クラスの分割やストラングラーパターンによる段階的な置き換えは、一度に全てを書き換えるのではなく小さな安全なステップに分解する発想が重要で、AIに任せる際もこの段階的なアプローチを指示することでリスクを抑えられる。

🔧 やってみよう

マジックナンバーが混じった関数を1つ選び、既存テストで振る舞いが変わっていないことを確認しながら定数化・早期リターン・メソッド抽出を行う。所要目安: 1時間。
